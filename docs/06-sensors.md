# Датчики

> **Статус.** Драйверы RV-3032, VL53L0X, AHT20 и BMP280 написаны, но на реальном
> железе не проверялись — целевого компилятора на машине разработчика не было.
> Проверены только синтаксис и типы. MPU6050 и OLED проверены. Если что-то из
> четвёрки ведёт себя не так, как здесь описано, — начинайте с шины
> ([05-i2c.md](05-i2c.md)), затем читайте реализацию в `drivers/src/`.

## Общий шаблон

Четыре датчика (RV-3032 — частично) следуют одной схеме:

| Функция | Роль |
|---|---|
| `..._init()` | настроить чип, один раз при старте |
| `..._whoami(&id)` | идентификатор чипа, можно звать до `init` |
| `..._start()` | запустить одно измерение, вернуться сразу |
| `..._ready(&flag)` | готов ли результат |
| `..._get(...)` | забрать результат |
| `..._measure(...)` | `start` + ожидание + `get`, блокирующе |

`measure()` — то, что нужно в 90% случаев:

```c
int32_t t; uint32_t p;

if (hexa_bmp280_measure(&t, &p) == HEXA_OK)
        xprintf("p=%u Pa\n", p);
```

### Зачем тогда `start`/`ready`/`get`

Потому что измерение занимает время, и не всегда его можно проспать.
AHT20 считает ~80 мс, VL53L0X — ~30 мс. Задаче, которая между делом обслуживает
кнопки или рисует на экране, блокироваться на такой срок нельзя.

Раздельный интерфейс позволяет вписать датчик в цикл, не останавливая его:

```c
enum { IDLE, WAIT } st = IDLE;

while (1) {
        hexa_button_scan();             /* работает всегда */

        switch (st) {
        case IDLE:
                if (hexa_aht20_start() == HEXA_OK)
                        st = WAIT;
                break;

        case WAIT: {
                bool ready = false;
                if (hexa_aht20_ready(&ready) == HEXA_OK && ready) {
                        int32_t t; uint32_t rh;
                        hexa_aht20_get(&t, &rh);
                        st = IDLE;
                }
                break;
        }
        }

        hexa_delay_ms(10);
}
```

Драйвер не решает за приложение, можно ли ему блокироваться, — он даёт оба
варианта, а `measure()` просто собран из тех же кирпичей.

Под FreeRTOS блокирующий `measure()` обычно и правильный выбор: пока задача
спит в `hexa_delay_ms()`, процессор занят другими. Раздельный интерфейс нужен
в bare metal и в задачах с жёстким временем реакции.

Шаг опроса внутри `measure()` — 10 мс, ровно один тик планировщика
(`configTICK_RATE_HZ = 100`). Меньше брать нельзя: `pdMS_TO_TICKS(5)` даёт ноль,
`vTaskDelay(0)` уступает процессор, но не выжидает, и заявленный таймаут
перестаёт соответствовать реальному времени.

## Почему всё в целых числах

У процессора нет FPU, и собирается всё под `-mabi=ilp32` (см.
[02-project.md](02-project.md)). Любая операция с `float` — вызов программной
библиотеки: десятки инструкций вместо одной и лишние килобайты кода. Плюс
`xprintf` не умеет печатать плавающую точку в принципе.

Поэтому единицы фиксированы и целочисленны:

| Величина | Единица | Пример |
|---|---|---|
| температура | сотые доли °C | `2534` = 25.34 °C |
| влажность | сотые доли %RH | `4780` = 47.80 %RH |
| давление | паскали | `101325` |
| дистанция | миллиметры | `842` |
| акселерометр/гироскоп | сырые отсчёты АЦП | `16384` = 1 g |

Печать «дробного» значения — деление и остаток, отдельной функцией. Ровно так
сделано в `examples/rv3032` и `examples/aht20_bmp280`:

```c
static void print_c100(int32_t v)
{
        const char *sign = (v < 0) ? "-" : "";
        uint32_t a = (uint32_t)((v < 0) ? -v : v);

        xprintf("%s%u.%02u", sign, a / 100, a % 100);
}
```

Знак обрабатывается отдельно: у `-5` деление на 100 даёт `0`, и без явного
`sign` получилось бы `0.05` вместо `-0.05`. Ширина `%02u` обязательна, иначе
`2504` напечатается как `25.4`.

Если дробная арифметика всё же нужна — считайте в целых с масштабом (сотые,
тысячные), а делите один раз в конце.

## MPU6050 — акселерометр и гироскоп

```c
#include "hexa_mpu.h"

hexa_status_t hexa_mpu_init(void);
hexa_status_t hexa_mpu_whoami(uint8_t *id);                     /* 0x68 */
hexa_status_t hexa_mpu_read_accel(int16_t *x, int16_t *y, int16_t *z);
hexa_status_t hexa_mpu_read_gyro (int16_t *gx, int16_t *gy, int16_t *gz);
```

Здесь нет `start`/`ready`: чип меряет непрерывно, чтение просто снимает
последние значения.

`init()` сбрасывает чип, ждёт 100 мс, выводит из сна и включает все три оси.
Диапазоны остаются заводскими:

| | Диапазон | Масштаб |
|---|---|---|
| акселерометр | ±2 g | 16384 отсчёта на 1 g |
| гироскоп | ±250 °/с | 131 отсчёт на 1 °/с |

Перевод драйвер не делает намеренно: он зависит от диапазона, а держать
пересчёт в драйвере значит навязать приложению единицы и потерять точность на
целочисленном делении. В сотых долях g:

```c
int32_t ax_g100 = (int32_t)ax * 100 / 16384;
```

Идентификатор чипа удобно печатать до инициализации:

```c
uint8_t id;
hexa_mpu_whoami(&id);
xprintf("mpu whoami = 0x%02x\n", id);   /* ожидается 0x68 */
```

Пример: `examples/mpu6050/mpu.c`.

## RV-3032-C7 — часы реального времени

```c
#include "hexa_rv3032.h"

hexa_status_t hexa_rv3032_init(void);
hexa_status_t hexa_rv3032_time_valid(bool *valid);
hexa_status_t hexa_rv3032_get_time(hexa_datetime_t *dt);
hexa_status_t hexa_rv3032_set_time(const hexa_datetime_t *dt);
hexa_status_t hexa_rv3032_get_temp(int32_t *t_c100);
```

Это **внешний** чип на шине, не встроенный RTC микроконтроллера
(`mik32_hal_rtc.h`). Драйвера внутреннего RTC в SDK нет.

```c
typedef struct {
        uint8_t  sec;    /* 0..59 */
        uint8_t  min;    /* 0..59 */
        uint8_t  hour;   /* 0..23 */
        uint8_t  wday;   /* 0..6 */
        uint8_t  day;    /* 1..31 */
        uint8_t  month;  /* 1..12 */
        uint16_t year;   /* 2000..2099 */
} hexa_datetime_t;
```

`wday` — просто диапазон регистра чипа; какой день считать нулевым, решает
приложение. Драйвер день недели не вычисляет и не проверяет на согласованность
с датой.

`set_time()` проверяет все поля и возвращает `HEXA_ERR_PARAM`, если что-то вне
диапазона.

**Главное правило: проверяйте `time_valid()` при старте.** Часы питаются от
собственного источника, и после первой подачи питания (или разряда) содержимое
регистров случайно. Флаг сбрасывается автоматически при удачном `set_time()`.

```c
bool valid;
if (hexa_rv3032_time_valid(&valid) == HEXA_OK && !valid) {
        const hexa_datetime_t init = {
                .sec = 0, .min = 0, .hour = 12,
                .wday = 1, .day = 1, .month = 1, .year = 2026,
        };
        hexa_rv3032_set_time(&init);
}
```

Полезная деталь реализации: `get_time()` читает 7 регистров одной пачкой, затем
перечитывает секунды и при расхождении повторяет чтение. Без этого раз в минуту
можно поймать время вида 12:59:00 вместо 13:00:00 — секунды успели перевернуться
в середине передачи.

У чипа нет регистра WHO_AM_I, поэтому `init()` только проверяет, что по адресу
кто-то отвечает. Регистры конфигурации в EEPROM драйвер не трогает.

`get_temp()` даёт встроенный термодатчик в сотых долях °C, разрешение чипа —
0.0625 °C, то есть младшие разряды будут кратны 6 сотым. Это температура
кристалла часов, а не окружающей среды.

Пример: `examples/rv3032/rv3032.c`.

## VL53L0X — лазерный дальномер

```c
#include "hexa_vl53l0x.h"

hexa_status_t hexa_vl53l0x_init(void);
hexa_status_t hexa_vl53l0x_whoami(uint8_t *id);   /* 0xEE */
hexa_status_t hexa_vl53l0x_start(void);
hexa_status_t hexa_vl53l0x_ready(bool *ready);
hexa_status_t hexa_vl53l0x_get(uint16_t *mm);
hexa_status_t hexa_vl53l0x_measure(uint16_t *mm); /* блокирует до ~100 мс */
```

**Самая хрупкая часть SDK.** У чипа нет публичной карты регистров: ST
распространяет только бинарно-подобный API с непрозрачными записями.
Последовательность инициализации восстановлена по этому официальному API, и
значительная её часть — магические записи, которые **невозможно обосновать по
даташиту**. Если драйвер сломается, отладка сведётся к сверке с исходниками
API ST, а не к чтению документации.

Что реализовано: data init, заводской набор tuning-настроек и опорная
калибровка (VHV + phase). Переконфигурация опорных SPAD не делается —
используются значения, загруженные чипом из NVM при включении. Для типового
применения этого достаточно, ценой будет чуть худшая устойчивость на пределе
дальности. Профиль по умолчанию — примерно до 1.2 м.

Ключевая особенность результата: **`HEXA_ERR` — это не поломка**. Так чип
сообщает, что измерение недостоверно (цель вне диапазона, слишком слабый
отклик, засветка). `*mm` при этом заполняется сырым значением, обычно 8190.
Различать «нет цели» и «сбой шины» нужно по коду возврата:

```c
uint16_t mm;

switch (hexa_vl53l0x_measure(&mm)) {
case HEXA_OK:
        xprintf("range = %u mm\n", mm);
        break;
case HEXA_ERR:
        xprintf("range = out of range (raw %u)\n", mm);
        break;
default:
        xprintf("range read FAIL\n");   /* вот это уже шина */
        break;
}
```

Измерение одиночное: каждый `start()` (и каждый `measure()`) запускает новый
цикл, результат готов примерно через 30 мс. Непрерывного режима драйвер не
поддерживает.

`get()` попутно сбрасывает флаг прерывания чипа. Пропустив `get()`, следующий
`ready()` будет возвращать `true` от старого измерения.

Пример: `examples/vl53l0x/vl53l0x.c`.

## AHT20 — температура и влажность

```c
#include "hexa_aht20.h"

hexa_status_t hexa_aht20_init(void);
hexa_status_t hexa_aht20_start(void);
hexa_status_t hexa_aht20_ready(bool *ready);
hexa_status_t hexa_aht20_get(int32_t *t_c100, uint32_t *rh_c100);
hexa_status_t hexa_aht20_measure(int32_t *t_c100, uint32_t *rh_c100);
```

Любой из указателей может быть `NULL`, если значение не нужно:

```c
int32_t t;
hexa_aht20_measure(&t, NULL);
```

Чип командный, а не регистровый, поэтому драйвер работает через
`hexa_i2c_*_raw()`.

`init()` начинается с паузы 100 мс — даташит требует её после подачи питания
до первой команды. Затем проверяется бит калибровки, и только если он не
выставлен, отправляется команда инициализации. Повторный вызов `init()` на уже
работающем чипе безвреден и быстр.

Преобразование — около 80 мс, таймаут в `measure()` — 200 мс.

`get()` проверяет CRC (полином 0x31) и при несовпадении возвращает
`HEXA_ERR_BUS` — это признак помех на шине, а не проблемы датчика. Если
результат ещё не готов, вернётся `HEXA_ERR`.

Пример: `examples/aht20_bmp280/aht20_bmp280.c`.

## BMP280 — давление и температура

```c
#include "hexa_bmp280.h"

hexa_status_t hexa_bmp280_init(void);
hexa_status_t hexa_bmp280_whoami(uint8_t *id);   /* 0x58 */
hexa_status_t hexa_bmp280_start(void);
hexa_status_t hexa_bmp280_ready(bool *ready);
hexa_status_t hexa_bmp280_get(int32_t *t_c100, uint32_t *p_pa);
hexa_status_t hexa_bmp280_measure(int32_t *t_c100, uint32_t *p_pa);
```

**Адрес.** По умолчанию `HEXA_BMP280_ADDR` = 0x76. У модуля с подтянутым к
питанию SDO адрес будет **0x77**. Драйвер сам его не ищет: правьте
`board/hexa_board.h`. На модуле GY-BMP280+AHT20 встречаются оба варианта —
сканирование покажет, какой ваш.

Чип держится в **forced mode**: одно преобразование по запросу, между
измерениями сон. Так проще согласовать с моделью `start`/`ready`/`get` и
дешевле по питанию, чем непрерывный normal mode. Плата за это — нужно явно
запускать каждое измерение.

Преобразование — около 10 мс, `measure()` блокирует до ~50 мс.

Температура считается всегда, даже если вам нужно только давление: компенсация
давления по заводским коэффициентам зависит от текущей температуры. `t_c100`
можно передать как `NULL` — считаться она всё равно будет.

Давление отдаётся в **паскалях**. Перевод в привычные единицы — целочисленный:

```c
/* 1 мм рт. ст. = 133.322 Па; считаем в десятых долях,
 * 110000 * 1000 ещё влезает в uint32 */
uint32_t mmhg10 = p_pa * 1000u / 13332u;   /* 101325 Па -> 7600 == 760.0 */
```

Если `whoami` даёт 0x58 — это BMP280. Значение 0x60 означает BME280 (с
влажностью): чип совместим по регистрам давления, но этим драйвером не
поддерживается.

Пример: `examples/aht20_bmp280/aht20_bmp280.c` — оба датчика на одной шине,
опрос раз в секунду.
