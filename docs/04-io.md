# Ввод-вывод: светодиод, кнопки, пищалка, отладочный вывод

## Светодиод

Драйвера светодиода в SDK нет — это один вывод GPIO, обёртка вокруг него ничего
не добавила бы. Примеры используют вывод `GPIO_2`, пин 7:

```c
#include <mik32_hal_gpio.h>
#include <mik32_hal_pcc.h>

static void led_init(void)
{
        GPIO_InitTypeDef gpio = {0};

        __HAL_PCC_GPIO_2_CLK_ENABLE();          /* без этого порт мёртв */

        gpio.Pin  = GPIO_PIN_7;
        gpio.Mode = HAL_GPIO_MODE_GPIO_OUTPUT;
        gpio.Pull = HAL_GPIO_PULL_NONE;
        HAL_GPIO_Init(GPIO_2, &gpio);
        HAL_GPIO_WritePin(GPIO_2, GPIO_PIN_7, __LOW);
}
```

Дальше `HAL_GPIO_WritePin()`, `HAL_GPIO_TogglePin()`, `HAL_GPIO_ReadPin()`.

Самая частая ошибка при работе с любым GPIO — забыть
`__HAL_PCC_GPIO_x_CLK_ENABLE()`. Порт без тактирования не сообщает об ошибке,
он просто ничего не делает.

Полный рабочий пример с миганием по таймеру — `examples/blink/blink.c`.

## Кнопки

```c
#include "hexa_button.h"

hexa_status_t hexa_buttons_init(void);
void          hexa_button_scan(void);
bool          hexa_button_down(uint8_t n);
bool          hexa_button_pressed(uint8_t n);
```

`n` — индекс в `hexa_pins_buttons[]` из `hexa_board.c`, считая с нуля, всего
`BOARD_BTN_COUNT` штук. Выход за границы — `false`, без падения.

Драйвер целиком построен вокруг `hexa_button_scan()`: он не пользуется
прерываниями, а опрашивает выводы и подавляет дребезг счётчиком. Состояние
кнопки меняется только после **четырёх подряд** одинаковых опросов. Отсюда
требование к периоду вызова: **1–10 мс**. Реже — реакция станет вязкой (при
50 мс переключение займёт 200 мс), чаще — счётчик наберётся быстрее дребезга
и фильтр перестанет работать.

Две функции опроса отличаются семантикой:

- `hexa_button_down(n)` — уровень: `true`, пока кнопку держат;
- `hexa_button_pressed(n)` — событие: `true` ровно один раз на нажатие, флаг
  сбрасывается при чтении. Внутри — критическая секция (`taskENTER_CRITICAL()`
  под FreeRTOS, запрет прерываний в bare metal), поэтому событие не потеряется,
  если `scan()` крутится в прерывании или в другой задаче.

Из `hexa_button_pressed()` следует, что читать её должен ровно один потребитель:
первый же вызов съедает событие.

```c
hexa_buttons_init();

while (1) {
        hexa_button_scan();

        if (hexa_button_pressed(0))
                xprintf("btn0 click\n");

        if (hexa_button_down(1))
                HAL_GPIO_WritePin(GPIO_2, GPIO_PIN_7, 1);
        else
                HAL_GPIO_WritePin(GPIO_2, GPIO_PIN_7, 0);

        hexa_delay_ms(10);
}
```

Под FreeRTOS опрос удобно вынести в отдельную задачу с `vTaskDelay(pdMS_TO_TICKS(10))`
— это ровно один тик ядра, минимально возможная и одновременно достаточная пауза.

Выводы настраиваются как вход **без подтяжки**, нажатой считается кнопка с
**высоким** уровнем на выводе. Внешняя подтяжка — на плате.

`hexa_buttons_init()` включает тактирование `GPIO_0` и `GPIO_1` сам.

> **Внимание.** Раскладка в `hexa_board.c` помечена `TODO` и не сверена с
> готовой платой: `BOARD_BTN_COUNT` равен 6, а инициализированы 5 элементов
> массива — у шестого `port == NULL`. Если кнопок действительно шесть,
> допишите вывод; если пять — поправьте `BOARD_BTN_COUNT`. Пока это не сделано,
> `hexa_buttons_init()` вызовет `HAL_GPIO_Init(NULL, ...)`.

## Пищалка

```c
#include "hexa_buzzer.h"

hexa_status_t hexa_buzzer_init(void);
hexa_status_t hexa_buzzer_tone(uint16_t tone);   /* частота в Гц */
hexa_status_t hexa_buzzer_off(void);
```

Звук делает аппаратный ШИМ: TIMER32_1, канал 2, скважность 50%. Канал 2
таймера TIMER32_1 выведен на `GPIO_0` пин 2 — это и есть `hexa_pin_buzzer`
в `hexa_board.h`. Тактирование `GPIO_0` нужно включить до `hexa_buzzer_init()`,
как это делает `examples/buzzer`:

```c
__HAL_PCC_GPIO_0_CLK_ENABLE();
hexa_buzzer_init();
```

Весь TIMER32_1 занят под пищалку — для других задач он недоступен.

`hexa_buzzer_tone()` **не блокирует**: звук включается и продолжается, пока не
позовут `hexa_buzzer_off()`. Длительность ноты отмеряет вызывающий. Так сделано
намеренно: драйвер не решает за приложение, можно ли ему сейчас блокироваться.

```c
hexa_buzzer_tone(440);
hexa_delay_ms(200);
hexa_buzzer_off();
```

`tone == 0` глушит звук и возвращает `HEXA_ERR_PARAM` — это не «сыграть тишину»,
а сообщение об ошибочном аргументе. Паузу в мелодии делайте явным
`hexa_buzzer_off()` плюс задержка, как в `examples/buzzer/buzzer.c`.

Период считается как `32000000 / tone`, то есть точность частоты падает к
верхнему краю диапазона. Для мелодий из нот это несущественно.

## Отладочный вывод: xprintf

`hexa_board_init()` инициализирует UART (9600 8N1, порт `UART_0`) и подключает
его к `xprintf` через `xdev_out()`/`xdev_in()`. После этого:

```c
#include "xprintf.h"

hexa_board_init();
xprintf("hello, %s! t=%d\n", "world", 42);
```

Напрямую `hexa_uart_putc()`/`hexa_uart_getc()` нужны редко. Обмен блокирующий:
вызов возвращается, когда байт ушёл. На 9600 бод один символ — это около
1 мс, то есть строка в 40 символов задержит выполнение почти на полсекунды.
В горячих циклах и под FreeRTOS в задачах с жёстким временем это заметно.

`\n` автоматически превращается в `\r\n` — терминалу дополнительный `\r`
слать не нужно.

### Поддерживаемые спецификаторы

| Спецификатор | Что печатает |
|---|---|
| `%d` | знаковое десятичное |
| `%u` | беззнаковое десятичное |
| `%x`, `%X` | шестнадцатеричное |
| `%o` | восьмеричное |
| `%b` | двоичное |
| `%s` | строка |
| `%c` | символ |
| `%ld`, `%lu`, `%lx` | то же для `long` |

Модификаторы: ширина поля (`%8d`), дополнение нулями (`%04x`), выравнивание
влево (`%-8s`), ширина из аргумента (`%*d`).

### Чего нет

**`%f` не поддерживается.** Плавающей точки в выводе нет вообще — ни `%f`,
ни `%e`, ни `%g`. И это не просто «не напечатает»: неизвестный спецификатор
печатается как обычный символ, а соответствующий аргумент **не снимается со
стека**. Все последующие аргументы поедут:

```c
xprintf("t=%f c, n=%d\n", 25.3, 7);   /* => "t=f c, n=<мусор>" */
```

Как печатать дробные значения — в [06-sensors.md](06-sensors.md): все датчики
отдают целые, и делятся они нацело.

Ещё есть `xsprintf(buf, fmt, ...)` — та же реализация, но в буфер. Удобно для
формирования строки перед выводом на OLED. Проверки переполнения буфера в ней
нет, размер считайте сами.
