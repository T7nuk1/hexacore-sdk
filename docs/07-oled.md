# OLED SSD1306

```c
#include "hexa_oled.h"

hexa_status_t hexa_oled_init(void);
hexa_status_t hexa_oled_clear(void);
hexa_status_t hexa_oled_pixel(uint8_t x, uint8_t y, uint8_t color);
hexa_status_t hexa_oled_print(const char *str, uint8_t x, uint8_t y, uint8_t color);
hexa_status_t hexa_oled_flush(void);

/* геометрия, координаты знаковые */
hexa_status_t hexa_oled_hline(int16_t x, int16_t y, int16_t w, uint8_t color);
hexa_status_t hexa_oled_vline(int16_t x, int16_t y, int16_t h, uint8_t color);
hexa_status_t hexa_oled_line(int16_t x0, int16_t y0, int16_t x1, int16_t y1, uint8_t color);
hexa_status_t hexa_oled_rect(int16_t x, int16_t y, int16_t w, int16_t h, uint8_t color);
hexa_status_t hexa_oled_fill_rect(int16_t x, int16_t y, int16_t w, int16_t h, uint8_t color);
hexa_status_t hexa_oled_circle(int16_t cx, int16_t cy, int16_t r, uint8_t color);
hexa_status_t hexa_oled_fill_circle(int16_t cx, int16_t cy, int16_t r, uint8_t color);
hexa_status_t hexa_oled_bitmap(int16_t x, int16_t y, int16_t w, int16_t h,
                               const uint8_t *bits, uint8_t color);
```

Монохромный дисплей 128×64 (`HEXA_OLED_WIDTH`/`HEXA_OLED_HEIGHT` в
`hexa_board.h`), адрес на шине 0x3C.

## Буфер кадра и flush

Рисование идёт **в оперативную память**, а не в дисплей. Пока не вызван
`hexa_oled_flush()`, на экране ничего не меняется:

```c
hexa_oled_clear();
hexa_oled_print("hexacore v0.0.1", 10, 10, 1);
hexa_oled_flush();
```

Так сделано не для красоты API, а потому что иначе не получится. У SSD1306 нет
чтения видеопамяти по I2C, а адресация в ней постраничная: одна ячейка — это
вертикальный столбик из 8 пикселей. Зажечь один пиксель, не зная состояния
семи соседних, невозможно. Локальная копия кадра решает это разом, заодно
убирая мерцание: экран обновляется целиком и одномоментно.

Плата — килобайт ОЗУ под буфер и цена самого `flush()`: 1025 байт по шине
одной посылкой. На ~100 кГц это порядка 100 мс. Отсюда правило: **рисуйте
сколько угодно, `flush()` вызывайте один раз в конце кадра.** Вызов `flush()`
после каждой строки — самая частая причина «дисплей еле шевелится».

Верхняя граница частоты обновления получается около 10 кадров в секунду, и всё
это время шина занята — под FreeRTOS остальные задачи в неё не попадут.

## Координаты и цвет

`x` — вправо, `y` — вниз, начало в левом верхнем углу. Пиксель за границей
экрана возвращает `HEXA_ERR` и игнорируется, ничего не портится.

| `color` | Действие |
|---|---|
| 0 | погасить |
| 1 | зажечь |
| любое другое | инвертировать |

Инверсия удобна для курсора или выделения: нарисовали поверх готового кадра
прямоугольник с `color = 2` — получили негатив в этой области.

## Текст

Шрифт 5×7, шаг между символами 6 пикселей, то есть в строке помещается 21
символ, а по высоте — 8 строк с шагом 8 пикселей.

Ограничения, о которых лучше знать заранее:

- **только ASCII 0x20..0x7E.** Кириллица и любые непечатаемые символы выводятся
  пробелом. Русский текст на экране не появится — в шрифте его нет.
- строка обрезается по правому краю экрана;
- переноса строк нет, `\n` — просто непечатаемый символ, то есть пробел.
  Вторая строка — второй вызов `print()` с другим `y`;
- фон не затирается: `print()` зажигает пиксели глифа и не трогает остальные.
  Чтобы перерисовать меняющееся значение, гасите область — проще всего
  `hexa_oled_clear()` на весь кадр.

Числа форматируются заранее, `xsprintf()` из `xprintf.h` (плавающей точки нет,
см. [04-io.md](04-io.md)):

```c
char line[22];

xsprintf(line, "t=%d.%02u C", t_c100 / 100, (unsigned)(t_c100 % 100));
hexa_oled_clear();
hexa_oled_print(line, 0, 0, 1);
hexa_oled_flush();
```

## Типичный цикл вывода

```c
#include "hexa_board.h"
#include "hexa_oled.h"

void app_main(void)
{
        hexa_board_init();

        if (hexa_oled_init() != HEXA_OK) {
                xprintf("oled init FAIL\n");
                return;
        }

        while (1) {
                hexa_oled_clear();              /* только буфер */
                hexa_oled_print("line 1", 0, 0, 1);
                hexa_oled_print("line 2", 0, 8, 1);
                hexa_oled_flush();              /* один раз за кадр */

                hexa_delay_ms(200);
        }
}
```

## Если экран пустой

1. `hexa_board_init()` вызвана до `hexa_oled_init()`? Без неё шина не настроена.
2. `hexa_oled_flush()` вообще вызывается? Самая частая причина.
3. Дисплей виден на 0x3C? Прогоните `hexa_i2c_scan()`, см.
   [05-i2c.md](05-i2c.md). Часть модулей SSD1306 сидит на 0x3D — тогда правится
   `HEXA_OLED_ADDR` в `hexa_board.h`.
4. `hexa_oled_init()` вернула `HEXA_OK`? Она отправляет пачку команд
   инициализации одной транзакцией и падает целиком, если чип не ответил.
5. Экран есть, но текста нет — проверьте `color`: `print(..., 0)` рисует
   чёрным по чёрному.

## Геометрия

Отрезки, прямоугольники, окружности и картинки. Всё рисуется в тот же буфер
кадра, что и текст, и точно так же появляется на экране только после
`flush()`.

### Знаковые координаты

Геометрия принимает `int16_t`, а не `uint8_t`, как `pixel()` и `print()`.
Разница не косметическая: фигура может начинаться за краем экрана, и это
нормальный случай, а не ошибка.

```c
hexa_oled_fill_rect(-10, -5, 40, 20, 1);   /* видимая часть нарисуется */
hexa_oled_circle(125, 60, 20, 1);          /* дуга в правом нижнем углу */
```

С `uint8_t` такое не выразить — `-10` превратилось бы в `246`, и
прямоугольник уехал бы к правому краю вместо левого. Отсюда и правило
возврата: фигура целиком за экраном — это `HEXA_OK` и пустой кадр, а не
ошибка. `HEXA_ERR_PARAM` возвращается только на заведомо бессмысленный
аргумент: нулевая или отрицательная ширина, `NULL` вместо картинки.

### hline/vline против line

`hexa_oled_line()` умеет всё, что умеют `hline` и `vline`. Отдельные функции
существуют потому, что горизонталь и вертикаль ложатся в видеопамять
байтами, а не пикселями:

- горизонтальный отрезок целиком лежит в одной странице, маска на все
  столбцы одна — считается один раз, дальше идёт запись подряд;
- вертикальный отрезок задевает каждую страницу ровно одним байтом — восемь
  пикселей пишутся одной операцией.

Поэтому заливка (`fill_rect`, `fill_circle`) собрана из `hline`, а рамка — из
`hline` и `vline`. Строго горизонтальный и строго вертикальный вызовы
`line()` сами уходят в них же, так что платить за универсальность не
приходится.

### Инверсия и двойная отрисовка

У `color = 2` есть свойство, о котором легко забыть: пиксель, закрашенный
дважды, возвращается в исходное состояние. Поэтому каждая функция
гарантирует, что не трогает свои пиксели по два раза — у `rect()` боковины
укорочены на пиксель, чтобы не пройти по углам повторно, а `fill_circle()`
заливается строками, а не симметрией средней точки, у которой строки
перекрываются.

Если собираешь фигуру сам — следи за этим же. Две пересекающиеся линии с
`color = 2` погасят точку пересечения.

### Картинки

Формат построчный, старший бит слева: строка занимает `(w + 7) / 8` байт,
`0x80` первого байта — самый левый пиксель, хвост последнего байта
игнорируется. Так по умолчанию отдают конвертеры вроде image2cpp, и так же
картинку видно глазами прямо в исходнике:

```c
static const uint8_t heart[] = {
        0b01101100,
        0b11111110,
        0b11111110,
        0b01111100,
        0b00111000,
        0b00010000,
};

hexa_oled_bitmap(60, 28, 8, 6, heart, 1);
```

Нулевые биты не трогаются вообще — картинка прозрачная и ложится поверх
готового кадра. Нужен непрозрачный фон — сначала `hexa_oled_fill_rect()` той
же области цветом 0.

Массив с `const` уезжает в SPIFI, а не в оперативку. Это важно: ОЗУ на плате
16 КБ, и килобайт из них уже занят буфером кадра.

### Чего по-прежнему нет

Ни прокрутки, ни второго шрифта, ни отсечения по произвольной области. Всё
это строится поверх существующих функций в коде приложения — буфер кадра
общий.

## Всё вместе

`examples/demo` — прошивка, которая задействует весь SDK разом: пять экранов
с датчиками, кнопки, пищалка, вся геометрия. Там же видно, зачем нужен
FreeRTOS: отрисовка держит шину ~100 мс, и в суперцикле нажатия за это время
терялись бы, а с отдельной задачей опроса кнопок — нет.
