# Два режима сборки

Режим выбирается одной строкой в `CMakeLists.txt` проекта:

```cmake
set(SDK_FREERTOS ON)    # есть — FreeRTOS, нет — bare metal
```

Она ставится **до** `include(sdk.cmake)`: по ней выбирается BSP, подключается
ядро FreeRTOS и определяется макрос `SDK_FREERTOS=1`, под которым драйверы
переключают своё поведение.

## Что вы получаете

| | bare metal | FreeRTOS |
|---|---|---|
| `main()` | `bsp/bsp_main.c` | `bsp/freertos/bsp_main.c` |
| `HAL_Init()` + тактирование | **делает приложение** | делает BSP |
| таймер SCR1 | **приложение** | BSP, как источник тика ядра |
| `app_main()` вызывается | напрямую из `main()` | из задачи, созданной BSP |
| `hexa_delay_ms()` | активное ожидание | `vTaskDelay()` |
| I2C из нескольких потоков | потоков нет | защищён мьютексом |
| накладные расходы | нулевые | ~8 КиБ кучи + код ядра |

## Bare metal

Весь BSP:

```c
extern void app_main(void);

int main(void)
{
        app_main();
        while(1) {}
        return 0;
}
```

Это всё. Никакого тактирования, никакой периферии — процессор работает на том,
что настроил загрузчик. Поэтому приложение обязано поднять систему само:

```c
void app_main(void)
{
        HAL_Init();
        system_clock_config();  /* своя копия, см. examples/blink */
        hexa_time_init();
        /* ... */
}
```

`system_clock_config()` — обычная функция приложения, а не часть SDK. Она
одинаково выглядит во всех bare-metal примерах (`blink`, `buttons`, `buzzer`):
включает генераторы, выбирает OSC32M системным источником и обнуляет делители
AHB/APB, получая 32 МГц. Копировать её из примера — нормальная практика.

Порядок важен: `hexa_time_init()` внутри вызывает `HAL_PCC_GetSysClockFreq()`
и запоминает частоту. Вызванная до настройки тактирования, она посчитает
задержки от неправильной частоты.

Если возвращаться из `app_main()` — управление уйдёт в `while(1)` в BSP, и
всё встанет. В bare metal `app_main()` обычно не возвращается никогда.

## FreeRTOS

BSP делает существенно больше:

```c
int main(void)
{
        HAL_Init();
        SystemClock_Config();

        __HAL_SCR1_TIMER_SET_DIVIDER(0);
        __HAL_SCR1_TIMER_ENABLE();

        xTaskCreate(app_main_task, "app_main",
                APP_MAIN_STACK, NULL, APP_MAIN_PRIO, NULL);
        vTaskStartScheduler();
        for (;;) {}
}
```

Тактирование и HAL уже подняты — в `app_main()` их трогать не нужно.

Параметры задачи, в которой живёт `app_main()`:

| Параметр | Значение |
|---|---|
| стек | 512 слов = 2 КиБ |
| приоритет | `tskIDLE_PRIORITY + 1` |
| имя | `app_main` |

Когда `app_main()` возвращается, обёртка зовёт `vTaskDelete(NULL)` — задача
корректно исчезает, планировщик продолжает работать. Это нормальный способ
завершить `app_main()`, раздав работу другим задачам:

```c
void app_main(void)
{
        hexa_board_init();
        xTaskCreate(sensor_task, "sensor", 512, NULL, tskIDLE_PRIORITY + 1, NULL);
        /* дальше делать нечего — задача app_main умрёт, sensor_task останется */
}
```

Второй вариант — остаться жить и уснуть навсегда, как в `examples/oled`:

```c
while (1) {
        vTaskDelay(portMAX_DELAY);
}
```

Пустой `while (1) {}` под FreeRTOS писать нельзя: задача с приоритетом выше
idle сожрёт весь процессор и остальные задачи никогда не выполнятся.

## Почему нельзя трогать таймер SCR1 под FreeRTOS

У SCR1 один машинный таймер (`mtime`/`mtimecmp`), и порт FreeRTOS для RISC-V
использует именно его как источник системного тика: `FreeRTOSConfig.h` задаёт
`configMTIME_BASE_ADDRESS` и `configMTIMECMP_BASE_ADDRESS`, а планировщик при
старте программирует `mtimecmp` исходя из `configCPU_CLOCK_HZ`.

Отсюда два запрета:

- **`HAL_Time_SCR1TIM_Init()` вызывать нельзя** — она обнуляет `mtime`. Тик
  ядра при этом уезжает в прошлое, и следующего прерывания придётся ждать
  целый оборот счётчика.
- Менять делитель или писать в `mtimecmp` из приложения тоже нельзя.

Поэтому `hexa_time_init()` под FreeRTOS — пустая функция. Звать её всё равно
стоит: тогда один и тот же код собирается в обоих режимах.

Если приложению нужен свой периодический таймер под FreeRTOS — берите
TIMER32_0 или TIMER32_2 (TIMER32_1 занят пищалкой) либо программные таймеры
ядра, предварительно включив `configUSE_TIMERS`.

## Границы FreeRTOS в этом SDK

Из `bsp/freertos/FreeRTOSConfig.h`:

| Параметр | Значение | Следствие |
|---|---|---|
| `configTICK_RATE_HZ` | 100 | **тик 10 мс** — задержки короче не работают |
| `configTOTAL_HEAP_SIZE` | 8 КиБ | на все задачи, очереди и мьютексы |
| `configMAX_PRIORITIES` | 7 | приоритеты 0..6 |
| `configMINIMAL_STACK_SIZE` | 256 слов | минимум для своей задачи |
| `configUSE_PREEMPTION` | 1 | вытеснение по приоритету |
| `configUSE_TIMERS` | 0 | программных таймеров нет |
| `configCHECK_FOR_STACK_OVERFLOW` | 0 | переполнение стека не ловится |

Главный подводный камень — тик 10 мс. `pdMS_TO_TICKS(ms)` считает
`ms * 100 / 1000` целочисленно, поэтому:

```c
hexa_delay_ms(5);    /* 0 тиков — просто taskYIELD(), задержки нет */
hexa_delay_ms(10);   /* 1 тик */
hexa_delay_ms(25);   /* 2 тика == 20 мс, а не 25 */
```

Если датчику нужна пауза в единицы миллисекунд — в этом режиме её взять
неоткуда: округляйте вверх до 10 мс.

Второе — куча в 8 КиБ. Каждая задача забирает из неё стек (в **словах**, то
есть `512` — это 2 КиБ) плюс блок управления. Три задачи по 512 слов уже
не влезут. `configUSE_MALLOC_FAILED_HOOK` включён, так что неудачное создание
задачи приведёт к срабатыванию хука, а не к молчаливому `NULL`.

Проверка стека выключена, поэтому переполнение проявляется не диагностикой,
а порчей соседних данных и странными зависаниями. Первое подозрение при
необъяснимом поведении многозадачного кода — маленький стек задачи.

## Что выбрать

Bare metal — когда задача одна и линейная: помигать, опросить кнопку, снять
показание и отправить. Меньше кода, полный контроль над временем, нет кучи.

FreeRTOS — когда независимых по времени дел несколько: датчик опрашивается
раз в секунду, экран обновляется десять раз в секунду, кнопки — каждые 10 мс.
Плюс `hexa_delay_ms()` перестаёт быть потерянным временем: пока одна задача
спит, работают остальные.

Промежуточного варианта нет, и это осознанно: два BSP проще, чем один
универсальный с флагами.
